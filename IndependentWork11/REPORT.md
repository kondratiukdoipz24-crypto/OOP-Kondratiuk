
# Звіт
## Самостійна робота №19

**Тема:** Дизайн винятків і політики retry: теорія та кейси Polly.

### 1. Мета роботи

Метою роботи було вивчити механізм обробки винятків у C#, створення власних типів винятків та використання бібліотеки Polly для підвищення відмовостійкості програм.

### 2. Власний тип винятку

Було створено клас `InsufficientFundsException`, який успадковується від `Exception`.

Він містить дві додаткові властивості:

- `RequestedAmount` — сума, яку потрібно зняти.
- `CurrentBalance` — поточний баланс рахунку.

Також реалізовано три стандартні конструктори: без параметрів, із повідомленням та з повідомленням і внутрішнім винятком.

У класі `BankAccount` реалізовано метод `Withdraw()`. Якщо запитана сума перевищує баланс, виникає власний виняток.

Для обробки помилки використано `try-catch-finally`.

### 3. Сценарій 1. Retry для зовнішнього API

**Проблема:** зовнішній API може тимчасово не відповідати через проблеми з мережею або перевантаження сервера.

**Обрана стратегія:** Retry з експоненційною затримкою.

**Реалізація:** створено `ResiliencePipelineBuilder` із `AddRetry`. Програма імітує дві невдалі спроби, після яких API відповідає успішно.

**Результат:** Polly автоматично повторює запит після помилки. У консолі відображаються номери спроб та повідомлення про помилки.

### 4. Сценарій 2. Circuit Breaker для бази даних

**Проблема:** якщо база даних тривалий час недоступна, постійні запити можуть додатково навантажувати систему.

**Обрана стратегія:** Circuit Breaker.

**Реалізація:** налаштовано мінімальну кількість запитів, частку помилок і тривалість блокування. Після достатньої кількості невдалих запитів Circuit Breaker відкривається.

**Результат:** наступні запити не виконуються, а відхиляються одразу. Це допомагає не перевантажувати несправний сервіс.

### 5. Сценарій 3. Retry + Timeout

**Проблема:** надсилання повідомлення може тривати надто довго, через що програма довго очікує завершення операції.

**Обрана стратегія:** поєднання Retry та Timeout.

**Реалізація:** встановлено обмеження часу виконання 300 мілісекунд і дві повторні спроби. Перша спроба триває довше за встановлений час, а наступна завершується успішно.

**Результат:** перша операція переривається через перевищення часу очікування. Polly запускає повторну спробу, яка завершується успішно.

### 6. Коли використовувати винятки, а коли Result<T>

Винятки доцільно використовувати для непередбачуваних ситуацій, які порушують нормальну роботу програми. Наприклад, якщо файл не вдалося відкрити або виникла помилка з'єднання з базою даних.

`Result<T>` краще використовувати для очікуваних ситуацій, наприклад, коли користувач вводить неправильні дані або запитаний товар не знайдено. У таких випадках помилка є звичайним результатом виконання, а не аварійною ситуацією.

### 7. Відповіді на контрольні запитання

**1. Поясніть різницю між підходами «кидати виняток» та «повертати Result». Наведіть приклад для кожного.**

Виняток використовується для ситуацій, які порушують нормальне виконання програми. Наприклад, при спробі зняти кошти, яких немає на рахунку, можна кинути `InsufficientFundsException`.

`Result` використовується для очікуваних невдалих результатів. Наприклад, під час пошуку товару метод може повернути результат, що товар не знайдено.

**2. Які три стандартні конструктори рекомендується реалізовувати у власному типі винятку?**

Рекомендується реалізувати конструктор без параметрів, конструктор із повідомленням та конструктор із повідомленням і внутрішнім винятком.

**3. Чим Circuit Breaker відрізняється від Retry? Коли який патерн доцільніший?**

Retry повторює операцію після тимчасової помилки. Circuit Breaker припиняє виконання запитів до сервісу після певної кількості помилок. Retry підходить для короткочасних збоїв, а Circuit Breaker — для тривалої недоступності сервісу.

**4. Для чого потрібен Bulkhead і яку проблему він вирішує?**

Bulkhead розділяє ресурси між різними операціями. Він не дозволяє збою одного сервісу зайняти всі доступні ресурси програми та вплинути на інші операції.

**5. Чому Jitter важливий при реалізації Retry з експоненційною затримкою?**

Jitter додає випадкову складову до часу очікування між повторними спробами. Це допомагає уникнути одночасного повторного надсилання великої кількості запитів до сервера.

**6. Які ризики виникають при застосуванні Retry до неідемпотентної операції?**

Якщо операція вже виконалася, але відповідь не надійшла, повторна спроба може виконати її вдруге. Наприклад, клієнту можуть двічі списати кошти. Для уникнення цього використовують унікальні ідентифікатори операцій та перевірку повторних запитів.

### 8. Висновок

Реалізувала сценарії Retry, Circuit Breaker і Retry + Timeout. Зрозуміла, що ці механізми допомагають програмам краще обробляти тимчасові збої та залишатися працездатними. Також навчилася розрізняти ситуації, коли потрібно використовувати винятки, а коли краще повертати Result.
